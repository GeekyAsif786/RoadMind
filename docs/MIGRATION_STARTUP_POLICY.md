# RoadMind Migration Startup Policy

Date: 2026-05-30

## Goal

Phase 3 removes the production anti-pattern of letting SQLAlchemy create or mutate schema implicitly at API startup. RoadMind now keeps development convenience while requiring Alembic-managed schema in production.

## Runtime Rules

### Development

`AUTO_CREATE_TABLES` defaults to `false` in `Settings`, `backend/.env.example`, and `docker-compose.yml`, so development builds its schema with `alembic upgrade head` exactly like production. If migrations are not current, development startup logs a warning instead of failing.

Development may still opt in explicitly:

```env
ENVIRONMENT=development
AUTO_CREATE_TABLES=true
```

When this mode is enabled, `Base.metadata.create_all(...)` runs for local convenience and startup logs a warning that the mode is development-only. A database created this way has no `alembic_version` row and will not match migration-built databases.

### Production

Production must use:

```env
ENVIRONMENT=production
AUTO_CREATE_TABLES=false
```

If production starts with `AUTO_CREATE_TABLES=true`, startup fails immediately.

If production starts with missing or out-of-date Alembic metadata, startup fails immediately.

### Development Seed Data

Docker Compose development runs with `AUTO_CREATE_TABLES=false` and builds the schema with `alembic upgrade head`. Sample data is inserted separately and explicitly:

```bash
docker compose exec backend python -m app.db.seed
```

The seed (`backend/app/db/seed.py`):

- runs only when `ENVIRONMENT` is `development` or `local` and refuses every other value, including `production`
- refuses to run unless the database is at the Alembic head
- is idempotent: before inserting, it checks existing intersection names case-insensitively using PostgreSQL `LOWER()` and skips any seed entry that matches an existing intersection regardless of capitalization; `ON CONFLICT (name) DO NOTHING` remains as a backstop for exact-name conflicts; existing intersection records are never updated or deleted, so their IDs and dependent records are preserved
- never creates or alters schema

## Migration Validation

RoadMind compares:

- the database revision from `alembic_version`
- the code revision head from `backend/alembic`

The app treats the database as current only when both match.

## Operator Workflow

Before starting production API processes:

```bash
cd backend
alembic upgrade head
alembic current
```

Then start the API with production settings.

## Known Follow-up: ORM Model / Migration Drift

Recorded 2026-11-02 at head `e5c1e605dfd1`. Not yet fixed.

On a database built from empty with `alembic upgrade head`, `alembic check` reports that the ORM metadata in `backend/app/models/domain.py` and the migrations disagree. The differences are limited to indexes, constraints, and nullability. Tables and columns match, and `intersections` is not affected.

- **Index naming/shape:** migrations create composite, descending indexes (for example `ix_traffic_intersection_time`, `ix_signal_plans_intersection_created`, `ix_predictions_intersection_created`, `ix_signal_phases_plan`, `ix_corridors_emergency`, `ix_emergency_events_active`). The models declare single-column `index=True` indexes with autogenerated names (for example `ix_traffic_observations_intersection_id`, `ix_signal_plans_intersection_id`). Some migration-only indexes (`ix_intersection_signal_states_updated_at`, `ix_model_evaluations_created_at`) are not declared in the models.
- **`users.username` / `users.email`:** migrations use a unique constraint plus a non-unique index. The models expect a unique index.
- **`traffic_observations.direction`:** nullable in the migrations, `NOT NULL` in the model.

Resolution should be a new, reviewed migration (or model updates that declare the migration indexes via `__table_args__`). Do not edit already-applied migrations. Until this is fixed, `alembic check` cannot be used as a CI gate, and `AUTO_CREATE_TABLES=true` databases will differ from migration-built ones.

## Why This Matters

`create_all()` can create tables but cannot safely express reviewed schema changes, data migrations, index changes, constraint changes, or downgrades. Alembic keeps schema changes explicit, reviewable, and repeatable across environments.
